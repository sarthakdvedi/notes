# RAG Evaluation Notes

## 1. Introduction to RAG Evaluation

- In AI interviews, interviewers rarely ask you to just code a RAG pipeline. Instead, they test your deep understanding of pipeline components and performance evaluation.
    
      
    
- **Definition:** RAG Evaluation is the systematic process of determining whether a RAG system is outputting accurate results and, if not, identifying which specific component failed.
    
      
    
- **Analogy:** Testing a DSA solution on LeetCode requires test cases. Similarly, evaluating a RAG pipeline requires a structured benchmark called a **Golden Dataset**.
    
      
    
- **Student-Teacher Analogy for Failure Modes:**
    
      
    - **LLM Failure (Generation Issue):** The student had access to correct notes but still failed the exam.
        
          
        
    - **Retrieval Failure (Context Issue):** The student failed because the teacher gave incomplete, irrelevant, or wrong notes.
        
          
        

---

## 2. Prerequisites: The Golden Dataset

- A **Golden Dataset** is a ground-truth dataset created to evaluate a RAG pipeline.
    
      
    
- **Components of a Golden Dataset:**
    
      
    1. `Question`: Sample user queries.
        
          
        
    2. `Ground Truth`: Verified ideal answers (human-generated or expert-approved).
        
          
        
- **Evaluation Frameworks:** Tools like **Ragas** and **TruLens** are commonly used to automate this evaluation process.
    
      
    

---

## 3. The RAG Triad & Key Evaluation Metrics

RAG evaluation measures two major stages: **Retrieval** and **Generation**. The framework revolves around 4–5 core metrics:

  

### A. Context Precision (Retrieval Stage)

- **What it measures:** Evaluates whether all retrieved context chunks are actually relevant to the user question, and if top-ranked chunks contain the highest concentration of relevant information.
    
      
    
- **Ideal State:** High precision means minimal noise/irrelevant chunks returned from the vector database.
    
      
    
- **Low Score Root Causes:** Poor chunking, weak embedding model, or incorrect top-K vector search retrieval.
    
      
    

### B. Context Recall (Retrieval Stage)

- **What it measures:** Evaluates whether the retriever fetched _all_ necessary context needed to answer the question, compared against the Ground Truth.
    
      
    
- **Ideal State:** High recall means no critical piece of information was left out.
    
      
    
- **Low Score Root Causes:** Chunk size is too small, `top_k` parameter is set too low, or distance metrics in the vector database need tuning.
    
      
    

### C. Faithfulness / Groundedness (Generation Stage)

- **What it measures:** Measures whether the generated answer is strictly grounded _only_ in the retrieved context chunks, without making up facts.
    
      
    
- **Ideal State:** High faithfulness means 0% hallucinations.
    
      
    
- **Low Score Root Causes:** System prompt is too weak/permissive, LLM temperature is set too high, or the LLM is overriding retrieved facts with its pre-trained knowledge.
    
      
    

### D. Answer Relevance (Generation Stage)

- **What it measures:** Evaluates whether the generated response directly answers the user's prompt without going off-topic or rambling.
    
      
    
- **Ideal State:** The response directly addresses what was asked without unnecessary filler.
    
      
    
- **Low Score Root Causes:** Poor system instruction, bad prompt formatting, or LLM failing instruction-following.
    
      
    

### E. Answer Correctness / Semantic Similarity (Overall System)

- **What it measures:** Compares the final generated answer directly against the `Ground Truth` answer in the Golden Dataset to verify factual and semantic alignment.

## 4. Diagnostic & Debugging Framework (How to Fix Issues)

|**Problem Identified**|**Failing Metric**|**Recommended Fix / Action**|
|---|---|---|
|**Noise in Context**|Low Context Precision|Change chunking strategy, switch to a better embedding model, or implement a **Reranker**.|
|**Missing Information**|Low Context Recall|Increase `top_k`, enlarge chunk size, or use Hybrid Search (Keyword + Vector Search).|
|**LLM Hallucinating**|Low Faithfulness|Lower temperature to `0.0`, enforce strict prompt constraints (e.g., _"Answer ONLY using the provided context"_).|
|**Irrelevant Answer**|Low Answer Relevance|Fine-tune prompt structure, refine system role prompt, or use a stronger LLM model.|

---

## 5. Key Interview Takeaways & Engineering Philosophy

- **Iterative Process:** RAG tuning is an iterative loop. Adjust hyper-parameters (chunk size, overlap, `top_k`, temperature), re-run evaluation, and iterate until the system stabilizes.
    
      
    
- **No Perfect System:** Real-world engineering requires balancing precision and recall; achieving 100% across all metrics simultaneously is rarely realistic.
    
      
    
- **Role of AI Tools:** Tools like Claude or Copilot can write evaluation boilerplate syntax; the engineer's primary value lies in architectural decisions, metric selection, and systematic debugging based on evaluation scores.
