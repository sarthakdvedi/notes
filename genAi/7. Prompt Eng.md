# Prompt Engineering Notes

## Core Concept & Need for Prompt Engineering

- **Definition:** Prompt Engineering is the practice of refining inputs given to a Large Language Model (LLM) to produce consistent, predictable, and production-safe outputs.
    
      
    
- **Why LLMs Need Prompting:** LLMs are non-deterministic. Passing the exact same prompt multiple times can produce different responses, causing downstream code dependencies or software modules to crash.
    
      
    
- **Production Boundary & Security:** Unconstrained LLMs can drift into handling irrelevant tasks (e.g., answering coding or personal life questions inside a retail chatbot) or misclassifying unexpected user inputs.
    
      
    

---

## The 6 Essential Elements of a Production Prompt

To build stable, deterministic, and secure prompts, incorporate the following six structural components:

  

### 1. Role

- **Definition:** Sets the persona, domain, and specific responsibilities of the AI.
    
      
    
- **Key Interview Takeaway:** Defining a role guides response context, but **it does not increase the underlying model's intelligence or capability**.
    
      
    
- **Good:** `You are a customer support assistant at a laptop/mobile company`
    
      
    
- **Bad:** `You are a genius AI engineer` (does not boost intelligence)
    
      
    

### 2. Task

- **Definition:** Dictates the explicit, clear action the LLM must execute.
    
      
    
- **Example:** `You have to classify the issue into a category`
    
      
    

### 3. Constraints

- **Definition:** Establishes non-negotiable boundaries and rules for the model.
    
      
    
- **Example:** `You must classify the issue into only one of three categories: Billing, Technical, or Return`
    
      
    

### 4. Output Format

- **Definition:** Defines the exact structure, word limit, or syntax for the response so it can be reliably parsed by downstream code.
    
      
    
- **Example:** `Your answer should be in one word only. The word must be one of the categories given in Constraints`
    
      
    

### 5. Shots / Examples (Zero-Shot vs. One-Shot vs. Few-Shot)

- **Definition:** Providing sample inputs and desired outputs to guide model behavior by pattern matching.
    
      
    - **Zero-Shot:** No examples provided.
        
          
        
    - **One-Shot:** Single example provided.
        
          
        
    - **Few-Shot:** Multiple examples provided.
        
          
        
- **Example:** `For instance, if the user wants a refund, the category is Return`
    
      
    

### 6. Fallback

- **Definition:** Provides a safety handler or default behavior when inputs fall outside defined categories or bounds.
    
      
    
- **Why it Matters for Interviews:** Prevents hallucinated classifications on edge cases or malicious inputs.
    
      
    
- **Example:** `If the issue is completely unrelated to any category, output 'Other'`

## Summary of Code Demonstration (Before vs. After)

### Unengineered / Bad Prompt

Plaintext

```
This is a user complaint: "My laptop is not working". Handle this.
```

- **Output:** Generates verbose, inconsistent sentences or misclassifies completely out-of-scope inputs.
    
      
    

### Engineered / Production Prompt

RTC OF shot F

```
[ROLE] You are a customer support assistant at a laptop company.
[TASK] You have to classify the issue into a category.
[CONSTRAINTS] You have to classify the issue into one of three categories: Billing, Technical, or Return.
[OUTPUT FORMAT] Your answer should be in one word only.
[EXAMPLE] For instance, if the user wants a refund, the category is Return.
[FALLBACK] If the issue is unrelated to any category in Constraints, the answer should be "Other".
```

- **Output:** Consistently returns exact single-word strings like `Technical` or `Other`.
