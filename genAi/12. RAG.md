# 1. Summary of the Video

- **The Problem with LLMs:** LLMs (like ChatGPT) are trained on massive public internet data. However, they lack access to **private/internal domain knowledge** (e.g., company internal code, personal user details, or non-public databases). When asked about private data, LLMs often **hallucinate** (make up convincing but false answers) instead of stating they don't know.
    
- **What is RAG?** RAG stands for **Retrieval-Augmented Generation**. It is an AI architectural pattern used to supply external/private context to an LLM alongside a user's query so the LLM can output factually accurate responses.
    
- **Evolution of Solutions:**
    
    1. _System Prompts:_ Passing internal facts directly into the prompt works only for tiny, 1–2 line details.
        
    2. _Naïve File Uploads:_ Passing massive PDFs/documents directly to the LLM works for small scale, but quickly exceeds context limits and causes astronomical token costs on enterprise scale.
        
    3. _Naïve First-Iteration RAG:_ Fetching only specific relevant information using basic keyword lookup software and injecting it as context before calling the LLM.

# 2. Structured Notes (Instructor's Teaching)

### What RAG Means (Core Definition)

- **R — Retrieval:** Finding relevant internal facts/documents matching the user's prompt.
    
- **A — Augmented:** Feeding that retrieved information to the LLM as additional **context** inside the prompt.
    
- **G — Generation:** The LLM reads the context and generates the final accurate answer based _only_ on the provided information.
    

```
User Query ──► Retrieval Code ──► Extract Context ──► System Prompt + Query + Context ──► LLM ──► Accurate Answer
```

---

### Step-by-Step Breakdown: First Iteration RAG (Code Example)

1. **Step 1: Knowledge Base Creation** Store internal data in a local structure (e.g., Python `dict`, JSON, or text file).
    
    - _Example:_ `knowledge_base = {"age": "The age of Pratyush is 25 years", "networth": "The networth of Pratyush is ₹2000"}`
        
2. **Step 2: Simple Retrieval Function** Write custom software/logic to inspect the user query and return matching context.
    
    - _Example:_ If `"age"` in query $\rightarrow$ return `knowledge_base["age"]`.
        
3. **Step 3: Augment System Prompt & Generate Answer** Instruct the LLM to strictly answer using only the retrieved context:
    
    - _Prompt Instruction:_ `"Answer only based on this context. Do not hallucinate. Context: {retrieved_info}"`

### Why Naïve/First-Iteration RAG Fails (Interview Perspective)

While the basic RAG flow works for literal queries, Pratyush highlights severe real-world limitations of keyword-based retrieval:

1. **Semantic Inflexibility (Rigid Matching):**
    
    - Asking _"What is Pratyush's age?"_ matches the keyword `"age"` and works.
        
    - Asking _"How old is Pratyush?"_ fails completely because the word `"age"` isn't literally present, even though the meaning is identical.
        
2. **Typos & Misspellings:**
    
    - Small typos like _"aage"_ break strict string/keyword checks.
        
3. **Keyword False Positives:**
    
    - Asking _"What is age?"_ accidentally triggers and returns Pratyush's specific age, even though the question wasn't about him.
        
4. **Unscalable `if/else` Logic:**
    
    - You cannot manually write `if/else` conditions or synonym rules for thousands of variations in real enterprise data.
        

---

### Key Takeaway for Future Lessons

To overcome these rigid keyword limitations, production RAG systems upgrade the retrieval mechanism using concepts like **Embeddings, Tokenization, Chunking, and Vector Databases (e.g., Qdrant)**. However, the core underlying flow—_Retrieve $\rightarrow$ Augment $\rightarrow$ Generate_—remains identical.
